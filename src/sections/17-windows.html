C على Windows — زي ما بتشوفها في الـ Samples

أغلب الـ malware اللي هتحلله Windows. الكود بيبقى C عادي، بس مليان أنواع وAPIs خاصة بـ Windows. المرحلة دي مش عشان تكتب برامج Windows — دي عشان لما تشوف CreateMutexW أو RegSetValueExW في الـ imports أو الـ decompiler، تفهم فورًا السلوك اللي وراها.

الـ Hungarian Notation

lp = long pointer، sz = zero-terminated string، dw = DWORD، h = handle، cb = count of bytes، cch = count of characters. فـ lpszFileName = pointer لـ string اسم ملف، وcbData = حجم بالـ bytes. أسماء الـ parameters في MSDN بتقولك نوعها.

A و W: كل API ليها نسختين ANSI vs Unicode

CreateFile مجرد macro: بيبقى CreateFileW لو UNICODE متعرّف، أو CreateFileA. الـ A بتحول النص لـ UTF-16 وتنادي الـ W. في الـ imports هتشوف الاسم الحقيقي. والـ Native API (ntdll) بتستخدم struct خاص للنصوص:

UNICODE_STRING في الـ PEB

أسماء الـ DLLs في PEB->Ldr متخزنة كـ UNICODE_STRING (BaseDllName/FullDllName). لما تشوف shellcode بيقرا word ptr [rax+58h] (Length) وبعدها qword ptr [rax+60h] (Buffer) — ده بيقرا اسم الـ DLL من الـ LDR_DATA_TABLE_ENTRY عشان يلاقي kernel32.dll.

ليه الـ malware بينزل لتحت؟

أدوات الحماية (EDR) بتعمل hooks على دوال في ntdll/kernel32 عشان تراقب. فالـ malware المتقدم بينادي الـ Nt* مباشرة، أو بيعمل direct/indirect syscalls بنفسه. كمحلل: لو لقيت syscall instruction في كود الـ sample نفسه (مش جوه ntdll) = إشارة قوية على تقنية تهرّب، ولازم تعرف رقم الـ syscall (SSN) بيقابل أنهي دالة.

إزاي المحلل يتعامل مع الـ anti-debug

(1) اتعرف عليه: IsDebuggerPresent، gs:[60h] + [rax+2]، NtQueryInformationProcess بـ ProcessDebugPort (7)، timing checks بـ rdtsc/GetTickCount، البحث عن 0xCC. (2) عدّيه: plugin زي ScyllaHide في x64dbg، أو عدّل نتيجة الـ check (اقلب الـ ZF أو غيّر eax)، أو patch الـ jz لـ jmp. (3) وثّقه في الـ report كـ capability.
