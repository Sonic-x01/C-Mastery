الـ Threads والتزامن: أكتر من حاجة شغالة في نفس الوقت

أغلب الـ malware الحقيقي مش برنامج "خط واحد": فيه thread بيكلم الـ C2، وthread بيسجل الكيبورد، وthread بيراقب لو فيه debugger، والـ ransomware بيشغّل عشرات الـ threads عشان يشفّر أسرع. لما تفتح sample وتلاقي CreateThread أو pthread_create، لازم تعرف تلاقي الكود اللي هيتنفذ، وتفهم إزاي الـ threads بتتشارك البيانات من غير ما تبوظها.

🐧
قبل ما تبدأ الجزء ده

أمثلة الجزء الرابع بتستخدم APIs بتاعة Linux (POSIX): pthread، fork، الـ sockets، dlopen. زرار تشغيل بيشغّلها على Linux عادي. على جهازك استخدم WSL (الـ MinGW على Windows معندوش أغلبها). وهتلاحظ إن كل مثال بيبدأ بـ #define _POSIX_C_SOURCE 200809L قبل أي #include: إحنا بنعمل compile بـ -std=c17 الصارم، والسطر ده بيقول لـ glibc "اظهرلي دوال POSIX كمان". ولكل موضوع هتلاقي المقابل في Windows API، لأن ده اللي هتشوفه في أغلب الـ samples.

Process vs Thread concepts

الـ process = برنامج شغال ليه مساحة ذاكرة خاصة بيه (virtual address space). الـ thread = خط تنفيذ جوه الـ process. كل process بيبدأ بـ thread واحد (اللي بينفذ main)، ويقدر يعمل threads تانية. الـ threads كلها بتشوف نفس الذاكرة، وده سر قوتها ومصدر كل مشاكلها.

أول Threads: pthread_create و pthread_join pthread

الـ thread بيبدأ من دالة شكلها لازم يكون void *fn(void *arg). الـ void * ده هو الطريقة الوحيدة تبعت بيها بيانات للـ thread، فالنمط المعتاد: تعمل struct فيه كل اللي محتاجه، وتبعت عنوانه. وpthread_join بيستنى الـ thread لحد ما يخلص (زي wait للـ processes).

#define _POSIX_C_SOURCE 200809L #include #include typedef struct { int id; const int *data; size_t start, end; long sum; /* result, written by the thread */ } Job; static void *worker(void *arg) { /* the thread's entry point */ Job *job = arg; /* void* -> the real type */ for (size_t i = job->start; i < job->end; i++) job->sum += job->data[i]; return NULL; } int main(void) { int data[1000]; for (int i = 0; i < 1000; i++) data[i] = i + 1; pthread_t tid[4]; Job jobs[4]; for (int t = 0; t < 4; t++) { jobs[t] = (Job){ .id = t, .data = data, .start = (size_t)t * 250, .end = (size_t)(t + 1) * 250 }; if (pthread_create(&tid[t], NULL, worker, &jobs[t]) != 0) { fprintf(stderr, "pthread_create failed\n"); return 1; } } long total = 0; for (int t = 0; t < 4; t++) { pthread_join(tid[t], NULL); /* wait for thread t to finish */ printf("thread %d: sum[%zu..%zu) = %ld\n", jobs[t].id, jobs[t].start, jobs[t].end, jobs[t].sum); total += jobs[t].sum; } printf("total = %ld\n", total); return 0; }

ليه كل thread ليه Job خاص بيه؟

لو بعتّ عنوان متغير واحد لكل الـ threads وغيّرته في الـ loop، كلهم هيقروا آخر قيمة (أو قيمة في النص). القاعدة: البيانات اللي بتبعتها للـ thread لازم تفضل عايشة ومتغيرتش لحد ما الـ thread يخلص. لاحظ كمان إننا بنطبع بعد الـ join بس، عشان ترتيب المخرجات يبقى ثابت.

🔬
فين الكود اللي الـ thread هيشغّله؟

دالة الـ thread مش بتتنادى بـ call في أي حتة في البرنامج، فـ Ghidra ممكن ميعرفش إنها كود أصلًا. اللي هتلاقيه: عنوانها بيتحط كـ argument: في pthread_create هو الـ argument التالت (rdx)، وفي CreateThread على Windows هو التالت برضه (r8، اسمه lpStartAddress)، والـ argument الرابع (r9) هو الـ void * اللي بيوصل للدالة. اتبع العنوان ده، سمّي الدالة thread_xxx، وحدد نوع الـ struct اللي بيوصلها. في x64dbg: حط breakpoint على أول الدالة، أو فعّل Break on Thread Start.

الـ Race Condition: ليه counter++ مش آمن data race

جملة counter++ شكلها خطوة واحدة، لكنها في الحقيقة 3 خطوات: اقرا، زوّد، اكتب. لو thread اتقطع بين القراية والكتابة، وthread تاني عمل نفس الحاجة، زيادة واحدة هتضيع. الكود ده نتيجته بتتغير كل مرة تشغله (ومعظم الوقت أقل من المتوقع):

#define _POSIX_C_SOURCE 200809L #include #include static int counter; /* shared by all threads */ static void *inc(void *arg) { (void)arg; for (int i = 0; i < 1000000; i++) counter++; /* read-modify-write: NOT atomic */ return NULL; } int main(void) { pthread_t t[4]; for (int i = 0; i < 4; i++) pthread_create(&t[i], NULL, inc, NULL); for (int i = 0; i < 4; i++) pthread_join(t[i], NULL); printf("counter = %d (expected 4000000)\n", counter); return 0; } ; counter++ (gcc -O0) mov eax, DWORD PTR counter[rip] ; 1) read add eax, 1 ; 2) modify in a register mov DWORD PTR counter[rip], eax ; 3) write back ; another thread can run between 1 and 3! ; atomic_fetch_add(&counter, 1) (gcc -O2) lock add DWORD PTR counter[rip], 1 ; ONE indivisible instruction
💥
الـ Data race = Undefined Behavior

المعيار بيقول: لو two threads وصلوا لنفس المتغير ومنهم واحد بيكتب، من غير تزامن، ده UB. يعني النتيجة الغلط مش أسوأ حاجة ممكن تحصل: الـ compiler ممكن يحط المتغير في register ويعمل loop لا نهائي. الحل واحد من اتنين: mutex أو atomics.

Mutex: قفل على الـ Critical Section pthread_mutex

الـ mutex (mutual exclusion) قفل: thread واحد بس يقدر يمسكه في نفس الوقت، والباقي بيستنوا. الكود اللي بين lock وunlock اسمه critical section، وخليه أقصر ما يمكن.

#define _POSIX_C_SOURCE 200809L #include #include static long counter; static pthread_mutex_t lock = PTHREAD_MUTEX_INITIALIZER; static void *inc(void *arg) { (void)arg; for (int i = 0; i < 100000; i++) { pthread_mutex_lock(&lock); counter++; /* critical section */ pthread_mutex_unlock(&lock); } return NULL; } int main(void) { pthread_t t[4]; for (int i = 0; i < 4; i++) pthread_create(&t[i], NULL, inc, NULL); for (int i = 0; i < 4; i++) pthread_join(t[i], NULL); printf("counter = %ld (expected 400000)\n", counter); return 0; }
⚠️
الـ Deadlock

Thread A ماسك قفل 1 ومستني قفل 2، وthread B ماسك 2 ومستني 1، فالاتنين هيستنوا للأبد. القاعدة: لو محتاج أكتر من قفل، امسكهم دايمًا بنفس الترتيب في كل الكود. ولو نسيت unlock في مسار خطأ (return في النص)، نفس المشكلة، وده سبب نمط goto cleanup اللي شفته في المرحلة 04.

Atomics: عمليات مش بتتقسم stdatomic.h

لعمليات بسيطة زي عدّاد أو flag، الـ mutex تقيل. C11 فيها <stdatomic.h>: أنواع وعمليات الـ CPU بينفذها كخطوة واحدة (على x86 بـ prefix اسمه lock).

#define _POSIX_C_SOURCE 200809L #include #include #include static atomic_long hits; /* atomic counter */ static atomic_flag init_done = ATOMIC_FLAG_INIT; static void *worker(void *arg) { (void)arg; /* test_and_set returns the OLD value: only the first thread sees false */ if (!atomic_flag_test_and_set(&init_done)) puts("one-time init ran (exactly once)"); for (int i = 0; i < 100000; i++) atomic_fetch_add(&hits, 1); /* lock xadd / lock add */ return NULL; } int main(void) { pthread_t t[4]; for (int i = 0; i < 4; i++) pthread_create(&t[i], NULL, worker, NULL); for (int i = 0; i < 4; i++) pthread_join(t[i], NULL); printf("hits = %ld\n", atomic_load(&hits)); /* compare-and-swap: "if value == expected, replace it" in one step */ atomic_int owner = 0; int expected = 0; int won = atomic_compare_exchange_strong(&owner, &expected, 1234); printf("CAS #1 won=%d owner=%d\n", won, atomic_load(&owner)); expected = 0; won = atomic_compare_exchange_strong(&owner, &expected, 5678); printf("CAS #2 won=%d owner=%d (expected was updated to %d)\n", won, atomic_load(&owner), expected); return 0; }
🔬
الـ lock prefix في الـ disassembly

lock xadd، lock inc، lock cmpxchg = atomics. على Windows هتشوفها من InterlockedIncrement وInterlockedCompareExchange (الـ compiler بيعملها inline). وxchg مع الذاكرة atomic من غير lock. لما تلاقي lock cmpxchg جوه loop، ده غالبًا spinlock أو "run once" flag.

⚠️
volatile مش للـ threads

غلطة شائعة: volatile int counter; مش بتخلي counter++ آمن. volatile بتقول للـ compiler "اقرا واكتب من الذاكرة كل مرة، متخزنهوش في register"، وده مفيد لـ hardware registers، ولمتغيرات الـ signal handlers (المرحلة 19)، ومع setjmp. لكنها مش بتمنع الـ interleaving. وفي الـ samples، volatile بتظهر في anti-debug timing loops عشان الـ compiler ميشيلش الـ loop الفاضي.

Condition Variables: استنى لحد ما حاجة تحصل pthread_cond

أحيانًا thread لازم يستنى thread تاني يخلص حاجة (مثلًا: الـ config يتفك قبل ما thread الـ C2 يبدأ). الحل الغلط: loop بيلف ويسأل كل شوية (بيحرق CPU). الحل الصح: condition variable، الـ thread بينام لحد ما حد يصحيه.

#define _POSIX_C_SOURCE 200809L #include #include static pthread_mutex_t m = PTHREAD_MUTEX_INITIALIZER; static pthread_cond_t cv = PTHREAD_COND_INITIALIZER; static int config_ready; static char c2_addr[32]; static void *loader(void *arg) { (void)arg; pthread_mutex_lock(&m); snprintf(c2_addr, sizeof c2_addr, "%s", "10.0.0.5:443"); /* "decoded" */ config_ready = 1; pthread_cond_signal(&cv); /* wake up one waiter */ pthread_mutex_unlock(&m); return NULL; } int main(void) { pthread_t t; pthread_create(&t, NULL, loader, NULL); pthread_mutex_lock(&m); while (!config_ready) /* ALWAYS a loop (spurious wakeups) */ pthread_cond_wait(&cv, &m); /* releases m while sleeping */ printf("config ready: %s\n", c2_addr); pthread_mutex_unlock(&m); pthread_join(t, NULL); return 0; }

المقابل في Windows: Events (CreateEventW + SetEvent + WaitForSingleObject) أو CONDITION_VARIABLE. الـ events المسماة (named events) بتستخدم كمان للتواصل بين processes، واسمها IOC زي اسم الـ mutex.

Thread-Local Storage _Thread_local · TLS

متغير _Thread_local (في C23 اسمه thread_local) = global بس لكل thread نسخة. ده اللي بيخلي errno يشتغل صح مع الـ threads: كل thread ليه errno بتاعه.

#define _POSIX_C_SOURCE 200809L #include #include static _Thread_local int calls; /* one copy PER thread */ static void *work(void *arg) { int *result = arg; for (int i = 0; i < 5; i++) calls++; /* no race: nobody else sees this copy */ *result = calls; return NULL; } int main(void) { pthread_t t[3]; int results[3]; for (int i = 0; i < 3; i++) pthread_create(&t[i], NULL, work, &results[i]); for (int i = 0; i < 3; i++) { pthread_join(t[i], NULL); printf("thread %d saw calls = %d\n", i, results[i]); } printf("main thread's calls = %d\n", calls); return 0; }
🔬
fs: و gs: في الـ disassembly

الـ TLS بيتوصل له عن طريق segment register: على Linux x64 هو fs (مثلًا mov rax, QWORD PTR fs:0x28 = الـ stack canary من المرحلة 15). على Windows x64 هو gs وبيشاور على الـ TEB: gs:[0x30] = الـ TEB نفسه، وgs:[0x60] = الـ PEB. لما تلاقي mov rax, gs:[60h] ← movzx eax, byte ptr [rax+2]، ده قراية PEB->BeingDebugged، anti-debug من غير ما ينادي IsDebuggerPresent. وفي x86 (32-bit) نفس الكلام بس على fs:[0x30].

الـ Threads في الـ malware

(1) thread بيعمل loop فيه Sleep ثم beacon للـ C2. (2) thread بيفحص كل شوية لو فيه debugger أو أداة تحليل (watchdog). (3) thread pool للتشفير السريع في الـ ransomware (وغالبًا I/O Completion Ports: CreateIoCompletionPort). (4) CreateThread بـ flag CREATE_SUSPENDED (القيمة 4) ثم تعديل الـ context ثم ResumeThread: نمط injection. (5) CreateRemoteThread = thread جوه process تاني (المرحلة 17). وفي الـ debugging: لو الـ breakpoint بتاعك مش بيضرب، يمكن الكود شغال في thread تاني، فبص على تبويب Threads.

Race Conditions كثغرة: TOCTOU CWE-367

مش لازم threads عشان يبقى فيه race. Time-Of-Check to Time-Of-Use: البرنامج يتأكد من حاجة، وبعدين يستخدمها، وفي الفترة اللي بينهم حد تاني غيّرها. المثال الكلاسيكي: برنامج privileged بيعمل access("/tmp/report", W_OK) وبعدين open("/tmp/report"). بين السطرين، المهاجم يبدّل الملف بـ symlink لـ /etc/passwd. الحل: متفصلش الـ check عن الـ use، افتح الملف مرة واحدة واشتغل على الـ descriptor (open بـ O_NOFOLLOW، ثم fstat على نفس الـ fd).
