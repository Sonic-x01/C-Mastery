المرحلة الخامسة عشر

Undefined Behavior، فئات الثغرات، والحمايات — بعين المحلل

كتير من الـ malware بيدخل الأجهزة عن طريق ثغرة في برنامج مكتوب بـ C/C++ (مستند بيستغل PDF reader، صفحة بتستغل المتصفح، packet بتستغل خدمة). عشان تحلل الـ exploit chain أو تكتشف الـ bug في binary، لازم تفهم أنواع أخطاء الذاكرة وإزاي بتبان، وإيه الحمايات اللي الـ OS والـ compiler بيحطوها. المرحلة دي تحليلية ودفاعية.

Undefined Behavior: العقد اللي الـ Compiler بيصدّقه UB

الـ UB مش "النتيجة هتبقى غريبة". الـ UB معناه إن المعيار مبيقولش أي حاجة عن اللي هيحصل — والـ compiler بيفترض إنه مستحيل يحصل، وبيعمل optimizations على الأساس ده. والنتيجة: checks بتختفي، loops بتبقى لا نهائية، وكود بيتحذف.

#include #include #include static bool add_would_overflow(int a, int b) { return (b > 0 && a > INT_MAX - b) || (b < 0 && a < INT_MIN - b); } int main(void) { int tests[][2] = { { 100, 200 }, { INT_MAX, 1 }, { INT_MIN, -1 }, { -5, 3 } }; for (int i = 0; i < 4; i++) { int a = tests[i][0], b = tests[i][1]; if (add_would_overflow(a, b)) { printf("%11d + %2d -> overflow, refused\n", a, b); } else { printf("%11d + %2d = %d\n", a, b, a + b); } } /* GCC/Clang builtin: computes in infinite precision and reports overflow */ int r; if (__builtin_add_overflow(INT_MAX, 1, &r)) puts("__builtin_add_overflow caught it too"); return 0; }

اعرف الحمايات في ثواني

على Linux: checksec --file=./binary. على Windows: PE-bear / DIE / dumpbin /headers وشوف الـ DllCharacteristics (DYNAMIC_BASE، NX_COMPAT، GUARD_CF). وفي الكود: fs:28h (Linux) أو __security_cookie (Windows) في الـ prologue = canary. الـ malware نفسه غالبًا مبيتعملش compile بالحمايات دي — وده بحد ذاته معلومة عن بيئة الـ build بتاعته.

أدوات اكتشاف الأخطاء tooling

عادة المحترفين

أي parser أو tool بتكتبه لتحليل الـ samples (configs، PE، protocols) — شغّله بـ ASan وfuzzing قبل ما تعتمد عليه. الـ samples ممكن تكون معمولة مخصوص عشان توقّع أدوات التحليل، ومحلل اتعمله exploit عن طريق أداته = كارثة.

ليه gcc شال الـ check if (x + 1 < x) خالص؟ bug في الـ compiler لأن الـ signed overflow UB، فالـ compiler مسموحله يفترض إنه مبيحصلش، فالشرط دايمًا false لأن -O2 بيشيل كل الـ ifs لأن x مش متعمله initialize ده بالظبط إزاي الـ UB بيحذف security checks حقيقية. الـ check لازم يتعمل قبل العملية: x > INT_MAX - 1. إيه اللي المعيار بيقوله عن الـ signed overflow؟ في الـ disassembly قبل call memcpy: الطول جاي من packet وفيه cmp eax, 100h ثم jg error. المشكلة؟ مفيش مشكلة لازم je الحد صغير jg مقارنة signed: طول سالب (زي 0xFFFFFFFF) هيعدّي، وmemcpy هتعامله كرقم unsigned ضخم Signedness bug كلاسيكي (CWE-195). الـ check الصح يكون unsigned (ja) أو يرفض السالب صراحة. هل jg signed ولا unsigned؟ وmemcpy بتاخد الطول بأنهي نوع؟ شفت في prologue دالة على Windows: mov rax, cs:__security_cookie ثم xor rax, rsp ثم mov [rsp+...], rax. ده إيه؟ الـ stack cookie بتاع /GS (حماية من stack overflow) تشفير البيانات anti-debugging API hashing MSVC بيعمل XOR للـ cookie مع rsp ويخزنه، وفي الآخر بيعكس العملية وينادي __security_check_cookie. وجوده بيقولك إن الدالة فيها buffers على الـ stack. اسمه فيه "security cookie"… إيه الحماية اللي بتمنع تنفيذ كود اتكتب على الـ stack؟ ASLR Stack canary NX / DEP RELRO NX/DEP بيعلّم صفحات الـ stack والـ heap non-executable. عشان كده الـ malware (والـ exploits) بيحتاجوا VirtualProtect/VirtualAlloc بـ RWX عشان ينفذوا shellcode. أنهي حماية بتتحكم في صلاحية التنفيذ للصفحات؟ for (i = 0; i <= len; i++) buf[i] = src[i]; وbuf حجمه len. اسم الـ bug؟ Use-after-free Off-by-one (بيكتب byte واحد بعد الحدود) Format string Double free <= بيخلي آخر index = len وده برا الـ buffer.
