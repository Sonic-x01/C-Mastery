من C لـ Assembly: الـ Stack Frame، الـ Calling Conventions، والـ Optimizations

هنا بنربط كل حاجة. هتشوف الـ stack frame بالـ byte، الفرق الحقيقي بين Linux وWindows في استدعاء الدوال، وأشهر "حيل" الـ compiler اللي بتخلي الـ Assembly يبان غريب. بعد المرحلة دي، المفروض أي دالة -O0 تقراها في دقيقة، وأي دالة -O2 تفكها بالصبر.

تشريح الـ Stack Frame prologue · epilogue

#include int process(const char *input) { char buf[32]; int len = (int)strlen(input); strcpy(buf, input); /* unsafe on purpose */ return len + buf[0]; } process: push rbp ; save caller's frame mov rbp, rsp ; new frame base sub rsp, 64 ; room for locals mov QWORD PTR [rbp-56], rdi ; input mov rax, QWORD PTR [rbp-56] mov rdi, rax call strlen mov DWORD PTR [rbp-4], eax ; len mov rdx, QWORD PTR [rbp-56] lea rax, [rbp-48] ; &buf[0] mov rsi, rdx ; src = input mov rdi, rax ; dst = buf call strcpy movzx eax, BYTE PTR [rbp-48] ; buf[0] movsx edx, al ; char -> int mov eax, DWORD PTR [rbp-4] add eax, edx ; len + buf[0] leave ; rsp=rbp; pop rbp ret ; pop return address

في -O2 الـ frame pointer بيختفي

مع الـ optimization، gcc بيوقف استخدام rbp كـ frame pointer (-fomit-frame-pointer)، والمتغيرات بتبقى [rsp+X] أو في registers خالص. وفي Linux فيه red zone: الدوال الـ leaf (اللي مبتناديش حد) ممكن تستخدم 128 byte تحت rsp من غير sub rsp.

System V vs Microsoft x64 — نفس الكود calling conventions

الـ GCC يقدر يطلّع الـ convention بتاعة Windows بـ __attribute__((ms_abi))، فشوف الفرق بعينك (gcc -O2 حقيقي):

long callee6(long a, long b, long c, long d, long e, long f, long g); long sysv_caller(void) { return callee6(1, 2, 3, 4, 5, 6, 7); } __attribute__((ms_abi)) long win_callee(long a, long b, long c, long d, long e); __attribute__((ms_abi)) long win_caller(void) { return win_callee(1, 2, 3, 4, 5) + 1; } sysv_caller: ; Linux / System V sub rsp, 16 ; keep 16-byte alignment mov r9d, 6 ; arg6 mov r8d, 5 ; arg5 mov ecx, 4 ; arg4 push 7 ; arg7 -> stack mov edx, 3 ; arg3 mov esi, 2 ; arg2 mov edi, 1 ; arg1 call callee6 add rsp, 24 ; caller cleans up ret win_caller: ; Microsoft x64 sub rsp, 56 ; 32 shadow + args + align mov r9d, 4 ; arg4 mov r8d, 3 ; arg3 mov edx, 2 ; arg2 mov QWORD PTR [rsp+32], 5 ; arg5 ABOVE shadow mov ecx, 1 ; arg1 call win_callee add rsp, 56 add rax, 1 ret

علامة Windows x64 في أي function

لو شفت sub rsp, 28h (= 32 shadow + 8 alignment) في أول دالة بتنادي دوال تانية، ده Windows x64 بنسبة كبيرة. ولو لقيت mov [rsp+8], rcx وmov [rsp+10h], rdx في الأول — الدالة بتحفظ الـ args في الـ shadow space بتاعها (MSVC debug builds بتعمل كده).

Callee-saved: ليه push rbx في أول الدالة؟ register preservation

لو الدالة محتاجة register من الـ callee-saved (زي rbx أو r12) عشان يعيش قيمة عبر call، لازم تعمله push في الأول وpop في الآخر. عدد الـ push في الـ prologue = كام متغير "مهم" بتحتفظ بيه الدالة طول عمرها — غالبًا الـ arguments أو الـ loop counters.

رجوع struct كبير: الـ Hidden Pointer sret

struct big { long a, b, c, d; }; /* 32 bytes */ struct big make(long v) { struct big r = { v, v + 1, v + 2, v + 3 }; return r; } make: ; rdi = HIDDEN ptr to result lea rdx, [rsi+1] ; v is in rsi (2nd slot!) mov QWORD PTR [rdi], rsi mov rax, rdi ; return the hidden ptr mov QWORD PTR [rdi+8], rdx lea rdx, [rsi+2] add rsi, 3 mov QWORD PTR [rdi+16], rdx mov QWORD PTR [rdi+24], rsi ret

الـ struct الكبير (أكتر من 16 byte على Linux، أكتر من 8 على Windows) مش بيرجع في rax. اللي بينادي بيحجز مكان، وبيبعت عنوانه كـ argument أول مخفي — فكل الـ arguments الحقيقية بتتزحلق خانة! v هنا جه في rsi مش rdi. لو الـ decompiler بيوريك argument زيادة بيتكتب فيه وبيرجع — ده هو.

🔬
إزاي تفك الـ magic number

لو شفت imul بثابت ضخم وبعده shr بـ N: القاسم ≈ 2^N / magic. مثال: 2^35 / 0xCCCCCCCD = 34359738368 / 3435973837 ≈ 10.0 ← x / 10. ولو بعدها imul بالقاسم وsub من الأصل — ده x % 10. IDA وGhidra بيعملوا ده أوتوماتيك غالبًا، لكن لازم تعرف الشكل لما الـ decompiler يغلط.

#include #include /* Prove the compiler's trick: (x * 0xCCCCCCCD) >> 35 == x / 10 for every 32-bit x tested */ int main(void) { uint32_t samples[] = { 0, 9, 10, 99, 12345, 4294967295u }; for (int i = 0; i < 6; i++) { uint32_t x = samples[i]; uint32_t fast = (uint32_t)(((uint64_t)x * 0xCCCCCCCDull) >> 35); printf("%10u / 10 = %9u magic = %9u %s\n", x, x / 10, fast, x / 10 == fast ? "OK" : "MISMATCH"); } double approx = (double)(1ull << 35) / 0xCCCCCCCDu; printf("2^35 / 0xCCCCCCCD = %.6f\n", approx); return 0; }

منهجية فك أي دالة workflow

01

الـ Signature

أنهي registers بتتقرا قبل ما تتكتب؟ (= الـ args). إيه اللي في rax قبل ret؟ حجم الـ sub rsp؟

02

الـ Calls

أي call لـ API معروفة بيسمّي اللي حواليه: الـ args بتاعتها بتقولك أنواع المتغيرات (CreateFileW ← الـ arg الأول wide string path).

03

الـ Control Flow

حدد الـ loops (back-edges) والـ ifs. ارسم الـ graph في دماغك أو استخدم graph view.

04

الـ Data

كل [reg+offset] متكرر = struct. كل [base+i*size] = array. ثوابت كبيرة = magic/hash/crypto.

05

سمّي وعلّق

سمّي الدالة والمتغيرات والـ structs في Ghidra/IDA حتى لو التخمين مش أكيد (حط ?). الأسماء بتنتشر في كل الكود وبتوضح الصورة.

في الـ frame اللي فوق، الـ buf عند rbp-48. كام byte لازم تتكتب في buf عشان توصل لأول byte في الـ return address؟ 32 48 56 64 من rbp-48 لـ rbp+8 = 56 byte (48 لحد rbp + 8 للـ saved rbp). أول byte بعدهم = أول byte من الـ return address. المسافة من rbp-48 لحد rbp+8. على Windows x64، الـ argument الخامس لدالة بيتحط فين لحظة الـ call؟ [rsp+20h] — بعد الـ 32 byte shadow space r10 [rsp] rdi أول 4 في rcx, rdx, r8, r9، والـ shadow space (0x20) محجوز ليهم، فالخامس عند rsp+0x20. شفناها: mov QWORD PTR [rsp+32], 5. افتكر الـ 32 byte اللي الـ caller بيحجزها على Windows. شفت mov eax, 0AAAAAAABh ثم mul edi ثم shr edx, 1 والنتيجة في edx. ده غالبًا... x * 3 x / 2 x % 3 x / 3 (unsigned) mul بيحط النص العالي في edx = ضمني shift بـ 32، وبعدين shift 1: الإجمالي 33. 2^33 / 0xAAAAAAAB ≈ 3. القاسم ≈ 2^(32 + الـ shift) ÷ الـ magic. دالة بتاخد argument واحد في الكود، بس في الـ disassembly (Linux) بتكتب في [rdi] و[rdi+8]… و[rdi+24] وبترجع rdi في rax، والـ argument الحقيقي في rsi. التفسير؟ الدالة variadic بترجع struct كبير عن طريق hidden pointer في rdi الـ compiler غلط دي C++ this الـ struct الكبير بيرجع عن طريق pointer مخفي كأول argument، وبيترجع في rax كمان. (الـ C++ this برضو بيبقى في rdi/rcx — بس هنا الكتابة كلها في كل الـ fields والرجوع بيه هو علامة الـ sret.) شوف مثال make(). دالة بتبدأ بـ push r12، push rbp، push rbx. معنى ده؟ بتاخد 3 arguments بتحجز buffer هتستخدم 3 callee-saved registers لقيم لازم تعيش عبر الـ calls اللي جواها، فلازم تحفظ قيمهم القديمة anti-debugging الـ callee-saved registers لازم ترجع زي ما كانت. الـ push/pop حواليها بيقولك الدالة بتحتفظ بكام قيمة "طويلة العمر". مين لازم يحافظ على rbx وr12؟ اكتب بـ C الدالة دي (Linux ABI، x unsigned 32-bit) واطبع f(123456) وf(9) وf(1000):
