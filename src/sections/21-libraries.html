المرحلة الواحدة والعشرون

المكتبات: Static و Shared و DLLs (وإزاي الـ Malware بيستغلها)

نص الـ malware على Windows بييجي كـ DLL مش EXE: بيتشغّل بـ rundll32، أو بيتحقن في process تاني، أو بيتحط جنب برنامج شرعي عشان البرنامج يحمّله بالغلط (DLL sideloading). وعلى Linux، الـ userland rootkits بتشتغل عن طريق LD_PRELOAD. عشان تفهم ده كله، لازم تعرف المكتبة بتتبني إزاي، وبتتحمل إزاي، والـ loader بيدور عليها فين.

🔬
ليه الـ Linux malware غالبًا static؟

الـ bots زي Mirai بتتعمل compile static (غالبًا بـ musl أو uClibc) لكل architecture (ARM، MIPS، x86) عشان تشتغل على أي router من غير ما تعتمد على المكتبات اللي عليه. النتيجة: file بيقول statically linked, stripped، ومفيش ولا import. وبرامج Go وRust static by default. أول خطوة: طبّق signatures للمكتبة عشان تفرز كودها من كود الـ malware.

ابنِ مكتبة Static و Shared بإيدك ar · -fPIC

# xorlib.c contains: void xor_buf(unsigned char *b, size_t n, unsigned char k); # ---- static library ---- gcc -c -O2 xorlib.c -o xorlib.o # compile to an object file ar rcs libxor.a xorlib.o # archive = static library gcc main.c -L. -lxor -o app_static # code is COPIED into app_static nm app_static | grep xor_buf # T xor_buf (defined inside the exe) # ---- shared library ---- gcc -fPIC -shared -O2 xorlib.c -o libxor.so # -fPIC: works at any address gcc main.c -L. -lxor -o app_shared LD_LIBRARY_PATH=. ./app_shared # tell the loader where to look readelf -d app_shared | grep NEEDED # (NEEDED) Shared library: [libxor.so] ldd app_shared # which file each NEEDED resolves to nm -D libxor.so # dynamic symbols = the "exports"
💡
Position-Independent Code

الـ shared library بتتحمل في عنوان مختلف كل مرة (ASLR)، فكودها لازم يشتغل من أي عنوان. -fPIC بيخلي الـ compiler يستخدم عناوين نسبية لـ rip (lea rax, [rip+0x2f1a]) والـ GOT للمتغيرات الخارجية. وده نفس السبب إن الـ shellcode بيبدأ غالبًا بحيلة call $+5 ← pop rax: عشان يعرف هو فين في الذاكرة.

dlopen و dlsym: تحميل وقت التشغيل على Linux dlfcn.h

زي LoadLibrary + GetProcAddress (المرحلة 08) بالظبط: تحمّل .so وقت التشغيل وتجيب عنوان دالة بالاسم. الـ plugins بتشتغل كده، والـ malware بيستخدمها عشان الدوال متظهرش في الـ imports.

#define _POSIX_C_SOURCE 200809L #include #include typedef double (*math_fn)(double); int main(void) { void *lib = dlopen("libm.so.6", RTLD_NOW); /* load the math library */ if (lib == NULL) { printf("dlopen: %s\n", dlerror()); return 1; } const char *names[] = { "sqrt", "cbrt", "no_such_func" }; for (int i = 0; i < 3; i++) { dlerror(); /* clear old errors */ math_fn f = (math_fn)dlsym(lib, names[i]); /* void* -> fn pointer */ if (f == NULL) { printf("%-12s -> not found\n", names[i]); continue; } printf("%-12s(64.0) = %.2f\n", names[i], f(64.0)); } dlclose(lib); return 0; }

كود بيشتغل قبل main constructor · .init_array

GCC بيسمحلك تعلّم دالة إنها constructor: تتنفذ وقت تحميل الـ binary أو الـ .so، قبل main. عناوين الدوال دي بتتحط في section اسمه .init_array. والـ destructor بيتنفذ بعد ما main ترجع.

#include __attribute__((constructor)) static void early(void) { puts("constructor: runs before main (from .init_array)"); } __attribute__((destructor)) static void late(void) { puts("destructor : runs after main returns (from .fini_array)"); } int main(void) { puts("main : running"); return 0; }
🔬
متبدأش من main

أي .so فيها constructor بتشغّل كود بمجرد تحميلها، من غير ما حد ينادي أي دالة. ده بالظبط اللي بيعمله الـ malware بـ LD_PRELOAD. في Ghidra/IDA: بص على .init_array (Linux)، والـ TLS callbacks (المرحلة 16)، وDllMain (Windows)، والـ static constructors في C++ (المرحلة 22). أي واحد منهم ممكن يكون فيه anti-debug أو unpacking قبل ما توصل لـ main.

Symbol Interposition و LD_PRELOAD: إزاي الـ Hooking بيشتغل RTLD_NEXT

لما برنامج ينادي puts، الـ dynamic loader بيدور على الاسم في المكتبات بالترتيب، وأول تعريف يلاقيه هو اللي بيكسب. فلو فيه تعريف لـ puts قبل libc، هو اللي هيتنادي. وبعدين يقدر ينادي الأصلية عن طريق dlsym(RTLD_NEXT, "puts"). هنا بنعمل الحكاية جوه نفس البرنامج عشان تقدر تشغّلها:

#define _GNU_SOURCE /* for RTLD_NEXT */ #include #include #include typedef int (*puts_fn)(const char *); /* OUR puts: found before libc's, so every puts() call lands here */ int puts(const char *s) { static puts_fn real_puts; if (real_puts == NULL) real_puts = (puts_fn)dlsym(RTLD_NEXT, "puts"); /* the next one = libc */ if (strstr(s, "secret") != NULL) return real_puts("[hook] line filtered"); /* hide / change data */ fputs("[hook] ", stdout); return real_puts(s); } int main(void) { puts("listing files..."); puts("secret_backdoor.so"); puts("report.pdf"); return 0; }

بالظبط نفس الكود ده لو اتعمل compile كـ .so واتحط في LD_PRELOAD (أو في /etc/ld.so.preload لكل البرامج على الجهاز)، هيعمل hook لـ puts في أي برنامج. الـ userland rootkits (زي Jynx2 وAzazel وSymbiote) بتعمل كده مع readdir وopen وfopen عشان تخبي ملفاتها وprocesses بتاعتها من ls وps وnetstat.

🔬
إزاي تكشف LD_PRELOAD rootkit

(1) cat /etc/ld.so.preload: لازم يبقى مش موجود أو فاضي. (2) cat /proc/<pid>/environ | tr '\0' '\n' | grep LD_. (3) cat /proc/<pid>/maps: أي .so غريبة متحملة. (4) استخدم أدوات static (busybox static) لأن الـ rootkit مبيقدرش يعمل hook لـ binary معندوش dynamic linking. (5) في الـ .so نفسها: nm -D هيوريك إنها بتصدّر دوال بأسماء دوال libc (readdir، fopen)، وده مش طبيعي، ومعاها dlsym + RTLD_NEXT (القيمة -1).

DLLs على Windows: exports و DllMain dllexport

#include /* Exported: appears in the DLL's Export Directory */ __declspec(dllexport) int __cdecl add_numbers(int a, int b) { return a + b; } /* rundll32-style entry: rundll32.exe mydll.dll,RunMe */ __declspec(dllexport) void CALLBACK RunMe(HWND hwnd, HINSTANCE hinst, LPSTR cmdline, int show) { (void)hwnd; (void)hinst; (void)show; MessageBoxA(NULL, cmdline, "RunMe called", MB_OK); } /* Called by the loader: keep it tiny (the loader lock is held!) */ BOOL WINAPI DllMain(HINSTANCE hinst, DWORD reason, LPVOID reserved) { (void)reserved; switch (reason) { case DLL_PROCESS_ATTACH: /* 1: DLL just loaded into a process */ DisableThreadLibraryCalls(hinst); break; case DLL_PROCESS_DETACH: /* 0: being unloaded */ break; case DLL_THREAD_ATTACH: /* 2 */ case DLL_THREAD_DETACH: /* 3 */ break; } return TRUE; /* FALSE on attach = load fails */ } gcc -shared -O2 mydll.c -o mydll.dll -Wl,--out-implib,libmydll.a # DLL + import lib objdump -p mydll.dll | grep -A6 "Export" # see the export table rundll32.exe mydll.dll,RunMe hello # call an export from the command line
🔬
تحليل DLL مشبوهة

(1) ابدأ من DllMain: لو reason == 1 وبعدها CreateThread، الـ payload بيشتغل بمجرد التحميل (الـ thread عشان يهرب من الـ loader lock). (2) بص على الـ exports: DllRegisterServer = بيتشغّل بـ regsvr32، وexport بأسماء غريبة أو بـ ordinal بس = غالبًا entry بيتنادى بـ rundll32. (3) لو الـ exports بتاعتها نفس أسماء DLL نظام (مثلًا version.dll) وكلها forwarded للأصلية (مثلًا GetFileVersionInfoW بيشاور على C:\Windows\System32\version.GetFileVersionInfoW) ما عدا واحدة أو اتنين، ده DLL proxy للـ sideloading. (4) في x64dbg: Options → Preferences → Events → DLL Entry عشان يوقف على DllMain.

DLL Sideloading (MITRE T1574.002)

لأن فولدر الـ application بيتدور فيه الأول، المهاجم بياخد برنامج شرعي موقّع (signed) بيحمّل DLL مش في KnownDLLs، ويحط جنبه DLL خبيثة بنفس الاسم. البرنامج الموثوق بيحمّلها ويشغّل كودها، والـ EDR شايف process موقّع. ده من أكتر التقنيات استخدامًا في هجمات الـ APT. علامته: exe موقّع في فولدر غريب (%TEMP%، %APPDATA%) وجنبه DLL مش موقعة. وفي Procmon: فلتر NAME NOT FOUND على .dll بيوريك كل الأماكن اللي البرنامج دوّر فيها.
